Guiding principles

01

Owned vs. referenced

Most entities exist only because this trip exists. Two don't — Place and Route are reusable knowledge a trip merely points at.

02

Declare your own bounds

Every trip-owned entity states its own date or time range and points up to its parent by id. Nothing stores a list of its children, and nothing stores a back-reference either.

03

Derive, don't store

Anything computable from stored facts stays uncomputed until read: a day's contents are a query, a layover is a gap between two Transits, sort order comes from a timestamp when one exists.

04

Plan status and booking status are independent

Every trip-owned entity tracks whether it's happening at all (planning/active/completed/cancelled) regardless of money. A separate, optional booking tracks only the reservation itself — present solely when a purchase applies.

05

Ref generalizes annotation

Notes attach to whatever they concern through a small polymorphic Ref — an entity, a date, or a range — instead of living inside the thing they annotate.

06

Every entity carries its own images list

A flat images: Image[] on every entity — including Place, since the live Google Places lookup this site uses deliberately excludes photos. A list, not a single field, so hand-sourced reference photos and personal photos taken on the trip itself can coexist later without a schema change. Deliberately not derived through a Place reference: an Activity or Stay can carry photos different from its Place's, and entities with no Place at all (Trip, Leg, Scenario, Note) still get a home for their own.

The Image shape, used by every entity's images list

type Image = {
  uri: string,             // Wikimedia Commons Special:FilePath link, an official
                            // site's own photo, or (later) a personal upload
  credit: string | null,   // attribution text — required by the license on most
                            // Commons photos; null for public-domain (NPS/USGS) or
                            // once-added personal photos
  caption: string | null,  // optional, shown under the photo if present
}

Status ladders

Plan status — status on every trip-owned entity (Trip, Leg, Stay, Transit, Activity). Is this part of the plan happening at all — independent of whether anything was purchased.
planning→ active→ completed /cancelled
Booking status — inside an optional booking on Leg, Stay, Transit, and Activity, present only when a reservation actually applies. Independent of plan status: a cancelled booking doesn't mean the stay itself is cancelled — you might rebook it elsewhere. A Package (see Stay) reuses this exact ladder for the same reason — whether the add-on itself has been purchased is independent of whether the Stay it belongs to is booked.
planning→ booked /cancelled

Example: a free, unreserved campsite you decide to skip is status: 'cancelled' with no booking at all. A hotel room the hotel cancels on you — while you're still figuring out where else to stay — is booking.status: 'cancelled' while the Stay itself stays status: 'planning'. Collapsing these into one field loses that distinction.

01
Trip-owned

Trip

The whole vacation. Root of everything else; nothing points up from here.

{
  _id: 'trip_alaska_2027',
  name: 'Alaska National Parks Vacation + Cruise',
  summary: 'A road-and-fly trip through interior and Arctic Alaska — Denali, …',
  startDate: '2027-06-26',
  endDate:   '2027-07-24',
  status: 'planning',        // planning | active | completed | cancelled
  travelers: [ { id: 'trav_brian', name: 'Brian Rodecap', age: 51 } ],
  images: [],             // hero image, per Guiding principle 06
}
  • startDate/endDate are declared independently of its Legs — an unbooked gap, like the open Lake Clark/Katmai block, shouldn't shrink the trip's apparent length just because nothing inside it is finalized yet.
  • No booking. A trip isn't itself a purchase — it's booked through what's inside it. Same reason its status ladder skips "booked" entirely.
  • travelers gained age once the cruise line's own booking confirmation supplied it per passenger — still just a lightweight embedded list, not the fuller per-traveler identity floated in Open threads.
  • travelers[].id gives each traveler a stable handle to link against — added once Package.travelers (see Stay) needed to reference specific travelers the same way every other cross-entity pointer on this page does: by id, not by restating name and hoping it never drifts. Still a small, additive step rather than the fuller per-traveler identity floated in Open threads — id exists to be pointed at, nothing more.
  • name is the display title shown as both the trip's hero headline and its card headline on the multi-trip landing screen — not a short internal slug. The folder name under docs/data/ (e.g. 2027-summer-alaska) is the actual stable identifier every URL and cross-trip reference uses; name is free to read well instead.
  • summary is optional, one paragraph, rendered as-is on the trip's Overview tab — added once a second trip made it clear this couldn't stay hardcoded page copy.
02
Trip-owned

Leg

One contiguous, differently-shaped chunk of the trip — the road/fly parks portion vs. the cruise.

{
  _id: 'leg_cruise',
  tripId: 'trip_alaska_2027',
  name: '7-night cruise',
  order: 2,
  startDate: '2027-07-17',
  endDate:   '2027-07-24',
  status: 'active',                // planning | active | completed | cancelled
  skeletonAuthority: 'operator',   // self | operator
  booking: {                       // optional — only when the whole leg is one bundle
    status: 'booked',
    cost: { amount: 9336.00, currency: 'USD' },
    confirmationNumber: 'MWVV6Q',
    depositPaidAt: '2026-08-06',    // added: the operator's own confirmation gave a
    finalPaymentDueAt: '2027-04-18', // deposit/final-payment split cost alone couldn't show
    passengers: [                   // added: per-passenger fare breakdown, only
      { name: 'Brian Rodecap', fare: { amount: 3319.00, currency: 'USD' } },
    ],
  },
  images: [],
}
  • skeletonAuthority describes only the leg's date↔location skeleton — who decided "Jul 19 = Juneau." It says nothing about how flexible the excursions and meals inside that day are; that's ordinary Activity territory regardless of which leg it's in.
  • status and booking are independent, same as on every other trip-owned entity: status tracks whether this leg of the plan is happening at all; booking exists only because the cruise happens to be bought as one bundled fare. The parks leg has no single purchase, so it carries only its lifecycle status.
  • depositPaidAt/finalPaymentDueAt/passengers extend the shared booking shape — added once the cruise line's actual booking confirmation supplied dates and a per-passenger fare split that a single cost number couldn't hold. Populated only where the source data has them (here, and mirrored on stay_cruise.booking for cost/confirmationNumber); every other booking on this page still uses the plain three-field shape. Ties into the "Booking as a formal type" open thread below.

The Package shape, used by Stay.packages

type Package = {
  _id: string,
  name: string,                                 // 'Princess Premier', 'Kennicott
                                                   // Glacier Lodge meal package'
  status: 'planning' | 'booked' | 'cancelled',  // same ladder as Booking.status
  cost: { amount, currency } | null,
  confirmationNumber: string | null,
  benefits: string[] | null,   // itemized perks, e.g. one line per inclusion —
                                 // not a fixed enum, since what a package bundles
                                 // varies too much across providers to normalize
  travelers: string[] | null,  // which Trip.travelers[].id this package
                                 // actually covers — ids, not names, so the
                                 // link survives a traveler's name changing —
                                 // null means the whole party (the common
                                 // case); a named subset (e.g. Princess
                                 // Premier, bought for only 2 of this trip's
                                 // 4 travelers) means every other traveler is
                                 // on the Stay's own standard, non-package
                                 // inclusions instead
}

  // Note (kind: 'info') concerning { entity: 'stay', id: 'stay_example_pacific' }
  // now, not an inline field — see the Note entity, below.
  booking: {
    status: 'booked',
    cost: { amount: 531.70, currency: 'USD' },  // amount actually charged —
                                                   // not the room/tax/credit line items
    confirmationNumber: null,                    // no separate hotel-native code
                                                   // was ever given for this booking
    bookedThrough: {                              // added: booked via a third-party
      name: 'Capital One Travel',                 // agent — this booking only ever
      confirmationNumber: 'H-MR3H7GQVN49P',        // had the agent's own code
    },

  • checkInAt/checkOutAt are real timestamps, not dates — check-in is 3pm, checkout is 11am, rarely midnight.
  • lodging mirrors the Place reference pattern (external id + label) plus type-specific detail a Google Place can't carry — room type and campsite are facts about the reservation, not the physical property. A free-text checkInInstructions field briefly lived here too, then moved out to a Note concerning the Stay — the same "facts get one home, referenced everywhere else" reasoning Package.note follows below, once description text stopped being a special case just because it happened to live on a specific field.
  • status and booking are independent, not one field. Most stays have both moving together, but not always — a free roadside camp never gets a booking at all, and a hotel that cancels your reservation doesn't retroactively cancel the stay if you plan to rebook elsewhere.
  • bedConfiguration/deckGroup/shipZone extend lodging for the cruise cabin — the same "type-specific detail a Google Place can't carry" reasoning that already justifies roomType/roomNumber/campsite, just for a berth instead of a hotel room. Populated only on stay_cruise; no hotel or campsite Stay needs them.
  • partySize/equipment/vehicleCount extend lodging the same way, surfaced by testing against a real paid campsite reservation: federal campgrounds book against occupancy, equipment type, and vehicle count as hard constraints on the reservation itself, not incidental detail. Populated only where a campsite is actually reserved — a hotel Stay has no use for them.
  • What that test confirmed rather than changed: the reservation's cancel-by-date/refund-amount schedule ($5 refund through Jun 20, $0 after) maps cleanly onto a Note concerning the Stay, exactly like the cruise's cancellation schedule — no new field needed. And the order-level id (0878703196) versus this specific reservation's id (the -1 suffix) is the same bundle-booking-vs-item-booking split leg_cruise/stay_cruise already use, one level down.
  • bookedThrough extends booking, surfaced by testing against a real Capital One Travel hotel reservation whose only confirmation number belongs to the booking agent, not the hotel itself. Originally added as a flat name string with confirmationNumber left ambiguous ("whichever code manages the reservation") — promoted to { name, confirmationNumber } once the flight test (see Transit) proved a booking can carry two live codes at once, a vendor one and an agent one, that a single field can't hold. confirmationNumber now consistently means the vendor's own code, null when none was ever given, as here.
  • cost stays the flat amount actually charged, not a line-item breakdown — that same reservation's room/taxes/travel-credit split collapses to one number the same way a cruise fare or a campsite fee already does. No shape change; "derive, don't store" holds.
  • Payment method (masked card number, expiry) was deliberately left out, same reasoning as the Princess Captain's Circle numbers and on-file phone in the cruise test: an account identifier with no itinerary value, not worth the exposure in a public repo.
  • packages holds optional paid add-ons — a purchase distinct from both the base booking (which pays for the Stay itself) and an Activity's diningFormat: 'included' (bundled into the base rate at no extra decision). Princess Plus/Premier and a hotel's optional meal plan are the same shape: a single purchase, made once at the Stay level, that then covers many individual Activities. Surfaced by the Kennicott Glacier Lodge and Discovery Princess data — a meal previously modeled as diningFormat: 'included' with a note explaining it only counted "if the package is purchased" was really a distinct, not-yet-decided fact being smuggled into free text. Activity.diningFormat: 'package' plus an includedIn pointing at { entity: 'package', id } (see Activity) makes that fact structured instead: every Activity the package would cover references the one Package, so its purchase status lives in exactly one place rather than being repeated — and potentially drifting — per meal.
  • packages[].travelers scopes a package to whichever travelers actually bought it — surfaced once Princess Premier turned out to cover only 2 of this trip's 4 travelers, a fact that had briefly been smuggled into note as free text the same way the purchase-vs-included distinction above once was. null is the common case (a package everyone on the booking gets, e.g. a hotel's whole-room meal plan); a named subset means every other Trip.traveler is on the Stay's own standard inclusions instead for anything that package would otherwise cover. Points at Trip.travelers[].id, not name — every other cross-entity pointer on this page (legId, routeId, every Ref) links by id, and a name is exactly the field someone might reasonably edit later (a nickname, a legal-name correction) without meaning to break a package's coverage list. The trip page's day-list rows read this (via each Activity/MealOption's resolved traveler list — see trip-model.js's resolveMealTravelers, which turns the ids back into display names, and only resolves anything at all when diningFormat is 'package' — a plain 'included' meal, or any à-la-carte format, renders no chip, since nobody's coverage was ever gated on it) to show who's actually covered by a given purchased meal choice, not just whether one exists. Its non-meal sibling is Activity's own travelers (see below) — a package scopes who a purchase covers, while an excursion's own travelers scopes who's doing that activity, and the two are read by different rules precisely because a meal and an excursion answer "who's involved" differently.
  • Package no longer carries its own note field — that free-text caveat has the exact same shape as a MealOption's note (below): a fact worth recording, but not one this entity's own fields have a slot for. Both moved to a Note concerning { entity: 'package', id }/{ entity: 'mealOption', id } instead of staying inline, so the note gets the same kind (warning/info/footnote), the same edit/delete lifecycle, and the same drill-down placement every other annotation on this page already gets — rather than being a one-off string field that only this one entity happened to have.

One atomic, single-mode movement between two points.

  • Deliberately atomic. A multi-hop journey — walk to a bus stop, bus to the ferry — is several Transits sharing one journeyId, not one Transit with internal segments.
  • Layovers are never stored. They're the gap between one Transit's arrivesAt and the next one's departsAt within the same journeyId.
  • routeId/routeVariant record which reusable Route this specific movement followed, and which of that route's named alternatives was actually chosen.
  • arrivesAt is null whenever routeId is set — a routed drive's arrival is never an authored fact. A fixed "definitive" arrival stopped making sense once a real stop along the way (a lunch break with no fixed duration of its own) could push the true arrival later than whatever anyone might guess at authoring time, and once every reader of it derives from the walk anyway, there's nothing left for an authored value to do but go stale — so it's left blank and the computed view (trip-model.js's resolveTransitRoute) walks the Route's own place chain plus finalLegMinutes forward from departsAt instead, folding in any real Activity reached along the way. This walk isn't only run once at page load, either: app.js's recomputeRoutedTransits re-runs it live, right in the browser, whenever a route-variant tab or an in-transit meal's own option tab changes, so a picked route or a picked lunch format actually moves the displayed arrival instead of only changing its own row. A mode with a genuine external schedule (a flight's ticketed landing time, a ferry's posted arrival), or a Transit with no routeId at all, is the one case arrivesAt stays real and authored — there's no walk to prefer it over.
  • booking stays null for a drive in your own car — there's nothing to reserve, ever — while status still tracks whether this leg of movement is planned, underway, done, or scrapped.
  • scenarioId closes a gap the first migration pass surfaced: a drive-back whose departure time itself depends on which weather branch happened (e.g. a backup-flight day) couldn't be recorded at all without it — Activity could reference a Scenario, but Transit had no way to. It's the same reference used on Activity, reused here rather than inventing a second mechanism.
  • from/to gained placeId, matching Route's shape exactly — surfaced by testing against a real ferry reservation whose two terminals are genuinely resolvable points, unlike the regional labels ('Anchorage', 'Whittier') the original example used. Null for any endpoint that's really a whole city or a highway junction rather than one place; populated wherever a Transit's endpoint actually is one. The flight test confirms it unchanged — an airport is exactly the kind of single resolvable point the field was built for.
  • passengers[] needed no new field at all to cover the ferry. Transit shares Leg's booking shape by convention, and the per-passenger fare split already added there for the cruise covers a multi-traveler sailing exactly as designed — the first confirmation that extension isn't cruise-specific.
  • mode: 'ferry'/'flight' are just values, not a schema change — mode was always a free string, not a closed enum; drive, flight, and ferry all read the same way.
  • The cancellation terms (ferry's tiered per-ticket fees; the flight's "cancel by 11:59pm ET the next business day or it's non-refundable" and per-passenger, airline-set change fees) map onto a Note concerning the Transit — the first populated test of transit in Ref's entity union, which existed in the type already but had no real example until the ferry.
  • Order FPLZAS vs. each sailing's own booking number is the same bundle-vs-item split already confirmed on the campsite reservation — only the per-sailing confirmationNumber is stored; the order-level code is discussed here in prose, never a field.
  • carrier/flightNumber are new, mode-specific fields on Transit itself — not booking, since which specific flight actually moved you is a fact about the movement, independent of whether or how it was booked (you could know a flight number without ever reserving through this record). Same "detail the shared shape can't carry" reasoning that already justifies Stay's bedConfiguration/campsite, just on Transit and gated by mode instead of a lodging type.
  • passengers[].ticketNumber/seat extend the per-passenger entry — a flight, unlike the ferry, hands each passenger their own e-ticket number and (when selected) a seat assignment. Both optional, populated only when actually known.
  • bookedThrough's promotion to an object (see Stay) gets its first real payoff here: Delta's own PNR lands in confirmationNumber, Capital One's separate order code lands in bookedThrough.confirmationNumber — exactly the two-live-codes case that forced the shape change in the first place.

    {
      tone: 'scenic',
      label: 'Scenic — via the Seward Highway',
      places: [ { kind: 'waypoint', place: { id: 'ChIJ...', label: 'Girdwood' }, durationMinutes: 40,
               note: 'photo stop' },
             { kind: 'via', place: { id: 'ChIJ...', label: 'Portage Glacier / Whittier junction' },
               note: 'Anchorage–Whittier drives split off here', durationMinutes: 15 } ],
      finalLegMinutes: 20,  // drive time from the last place (or Depart, if none)
                             // to this route's own `to` — completes the chain
                             // places[].durationMinutes only carries stop-to-stop
    },
  ],
  images: [],
}
  • No tripId, no dates, no booking. The same trip, or a different trip entirely, can reference this route again.
  • variants[].tone has its own vocabulary — scenic/direct, deliberately not reusing Scenario's ideal/alternate. A route choice isn't a go/no-go safety branch.
  • variants[].places is an ordered sequence of places, not a bag of "vias." Each entry resolves to a real geo-point — a rule, not a convenience — and a Place ID is always tried first. coordinates: { lat, lng }, sitting alongside a plain label instead of place, is the fallback for the rare point Google's Places index genuinely has no entry for. What a place entry may never do is carry only a bare text label with neither. That used to be allowed ("places are loosely typed") until a computed map (the trip page's day-list map button, docs/js/trip-model.js's dayMapEmbedUrl) fed a bare label like 'Palmer' to Google's geocoder with no state/region qualifier and got a same-named town in a different state back — silently routing an Anchorage–Talkeetna drive through the Lower 48. A resolved Place ID or explicit coordinates can't be ambiguous the way free text can, which is the whole point of requiring one or the other.
  • Every place entry also carries a kind: 'waypoint' (a stop) or 'via' (no stop). A plain named highway ('Glenn Highway', 'Richardson Highway', 'George Parks Highway') turns out to have its own resolvable Google Place — but it's one fixed point for the entire, often 100+ mile road, not "wherever this particular route happens to be on it." This trip's data originally used those whole-highway Places as entries on multiple Route documents covering different real stretches of the same highway (e.g. 'Glenn Highway' as a stand-in for both the Anchorage–Palmer stretch and the Glennallen stretch, 150 miles apart) — since it's the same Place ID both times, the Directions URL link (dayFullRouteUrl) sent drivers on a real, absurd multi-hour detour toward whichever stretch the point actually sat on. The fix: a place entry is now either a waypoint — a real, individually-resolvable stop worth calling out (a town, a pass, a viewpoint) that's also safe to hand to Google's Directions API as a routing waypoint — or a via — a point that exists specifically to steer Directions off its default path onto the intended road (a fork, a cutoff, a side road) without stopping there, and still resolves to one real geo-point of its own rather than the whole highway's. A bare "you are now on Highway X" entry, with no distinct point and no steering purpose, isn't either — that information already lives in the variant's own label, so it was simply dropped rather than kept as a third kind.
  • places[].durationMinutes is the drive time from whichever place (or Depart) came before it — geography, same as the rest of Route, so it stays reusable across trips instead of being a discrete clock time that's only ever true for one specific departure. A trip's computed Day (trip-model.js's stageTimesForVariant) turns that into an actual estimated time by walking it forward from a specific Transit's departsAt, nudged later by any real Activity — a lunch stop, say — actually reached along the way. Superseded the earlier waypoints[] idea (a separate list of suggested stops with no timing at all): once every place already carries a real duration, a stop worth calling out is just an ordinary waypoint entry with a note, not a second parallel array — kind now carries the "is this really just a stop" distinction that array split used to.
  • variants[].finalLegMinutes completes the chain places[] leaves open. A place entry only ever carries the drive time to itself — nothing represents the remaining drive from the last named stop to the route's actual destination, so without this field a walked arrival would always land short of where the movement really ends. Surfaced once a routed Transit's arrival stopped being trusted from its own authored field (see Transit's arrivesAt rationale, above): the place chain plus this one closing number is what lets stageTimesForVariant walk all the way to a real arrival instead of stopping at the last place and clamping to a guess. Same status as every other duration on this page — geography, reusable across trips, never a discrete clock time.

Place

A real-world point, resolved live rather than duplicated. Pre-existing in the current site — the pattern everything else in this model was built to match.

{ id: 'ChIJS63CqrW_zlYRNQYObIK7Szk', label: 'Flying Squirrel Bakery Cafe', images: [] }

Named, but with no static geolocation to resolve — a restaurant aboard a moving cruise ship

{ id: null, label: 'Crown Grill', images: [] }
  • id is a pinned Google Place ID — hours, address, and website are fetched live, never stored redundantly.
  • Reused everywhere a real point is needed: Activity's place, Stay's lodging, Route's from/to/places[].place, and (as of the ferry test) Transit's from/to all share this exact shape.
  • images is the one field the live lookup can't fill in — the Places API call this site makes deliberately skips the Enterprise+Atmosphere fields (photos, rating, reviews) to avoid that pricing tier, so a stored, hand-picked photo is the only way a Place gets one at all. It's independent of whatever images an Activity or Stay that references this Place carries on itself — a restaurant's storefront photo and a specific dish photo for a meal there are different pictures.
  • id can be null — the same allowance Stay.lodging.placeId already makes for a named-but-unresolved location (a roadside pullout with no formal address), just generalized to every field that reuses this shape. Surfaced by two of this trip's own MealOption candidates: a cruise-ship specialty restaurant (Sabatini's, Crown Grill) has no static geolocation to resolve at all — the venue's location is relative to the ship, not the earth, the same reason stay_cruise.lodging.placeId is itself null — while a Ketchikan shore restaurant (Alaska Fish House, Annabelle's) has a real, resolvable address that just hasn't been looked up yet. Both read identically as id: null; the presentation tier renders label either way and simply skips the live Places lookup panel when id is absent (see places.js) rather than showing a loading state that can only ever resolve to "unavailable." Distinct from place: null itself, which still means no resolvable venue at all — self-catered, included with no venue to name, or genuinely not yet named.

Computed view — not stored

Day

No collection, no _id. What's happening on a given date is assembled at read time, not authored.

Assembled by, for a given date

find Stay  where checkInAt <= date < checkOutAt, on this Leg
find Transit where departsAt falls on this date, on this Leg
find Activity where startAt falls within that window, on this Leg
find Note  where concerns overlaps the date, the Leg, or any of the above
location := active Stay's lodging, or the relevant Transit's from/to
  • Nothing here has its own identity. Nobody books "July 5th" — every other entity on this page is a real thing in the world with a confirmation number, a ticket, or a geography. A day is a lens for grouping things that already have their own.
  • A Transit belongs to the day it departs, not every day it touches. An overnight sail or drive spans two calendar dates — but it's one trip event with one clock-time to sort by, and showing it a second time on the arrival day duplicated it in the timeline for no new information. location still falls back to an arriving Transit's destination on a day named after it (see arrivingTransit in trip-model.js's buildDay), even though the Transit itself only renders on the day it left.
  • Still essential to the presentation tier — and to how a human or an AI planning agent addresses the plan ("plan flightseeing on June 30") — just never as stored schema. The date is the handle; this query is what turns it into the structured entities that actually get touched.

The MealOption shape, used only by Activity.options

type MealOption = {
  _id: string,               // a mealOption Ref target — see Note's concerns, below
  diningFormat: 'included' | 'package' | 'sit-down' | 'grab-and-go' | 'drivethru' | 'self-catered',
  place: Place | null,      // same Place shape as Activity.place; null when there's no
                              // resolvable venue (included, package, self-catered, or not yet named)
  includedIn: Ref | null,   // set only when diningFormat is 'included' or 'package' — same
                              // rule as Activity.includedIn, just scoped to this one candidate
}
  • startAt/endAt are set only when actually known. timeLabel exists for the honestly-vague cases — "Afternoon" — instead of inventing false precision; see Activity's own timeLabel note above for its closed vocabulary and sort-anchor mapping.
  • booking is absent for most activities — a casual stroll never needs one — while status is always present, tracking the activity's own plan independent of whether it's reserved.
  • mealType/diningFormat/includedIn are two independent axes plus a pointer, not one field — which meal slot (or snack) this is, versus how the food actually happens, versus what's paying for it. Collapsing them (e.g. a single mealType: 'included-breakfast') would combinatorially explode the same way the model already avoids elsewhere (see Transit's mode rationale). A meal running late and becoming a drivethru instead needs no special structure to support — it's just editing diningFormat/place on an ordinary status: 'planning' Activity, the same flexibility every other field on this page already has.
  • An activity can be a meal without ever setting place. "Packed lunch" or "snacks from the cooler" is mealType: 'snack'/'lunch', diningFormat: 'self-catered', and no resolvable Place at all — same reasoning as Transit's from/to staying null for a whole city rather than forcing a point that doesn't exist.
  • includedIn reuses Note's Ref type rather than inventing a second polymorphic pointer — a bundled meal points at whichever Stay, Leg, or Activity's booking actually covers it, so cost and confirmation number stay owned by that one booking instead of being duplicated onto the meal itself. Set when diningFormat is 'included' (points at a { entity: 'stay', ... }, etc. — the base rate itself) or 'package' (points at a { entity: 'package', ... } — see Stay); every other format leaves it null.
  • 'included' and 'package' are deliberately separate diningFormat values, not one "covered somehow" flag — 'included' means the base rate already pays for it, no separate decision required; 'package' means it's covered only if a specific optional add-on gets purchased, and that purchase has its own planning/booked/cancelled status independent of the Stay. Collapsing them would either lose that distinction or force a not-yet-decided purchase to read as already-included.
  • options is the one genuinely new mechanism here, added once "which of these three places for breakfast" turned out not to fit the single-value fields at all — the three candidates can each have a different diningFormat (included / sit-down / grab-and-go), so the choice has to live per-candidate, not on the Activity itself. It mirrors Stay.lodging: null's "nothing chosen yet" — just extended to hold the actual named candidates instead of only recording that a decision is pending. diningFormat/place/includedIn stay null on the Activity the whole time options is set; deciding means picking one candidate, copying its three fields up onto the Activity itself, and clearing options back to null — the array never holds the decided state, only the open one.
  • MealOption carries its own _id even though it's an embedded array element, not a trip-owned collection — the one exception on this page to "only trip-owned entities get an id." A candidate's own free-text caveat (what used to be an inline note field) reads exactly like every other annotation on this page, so it became a Note like the rest, and a Note needs something stable to point concerns at — a bare array index would silently repoint at a different candidate the moment options gets reordered. _id survives reordering; it doesn't survive the candidate being promoted (options clearing to null once one's picked) — same as deleting any other entity a Note concerns, any Note still pointing at that id just has nothing left to render against.
  • priority is an enumerated rank, not a boolean — matching every other significance-style field on this page (status, mealType, diningFormat) rather than a loose highlight: true/false. Null for nearly everything; set only on the handful of activities worth calling out. It's what the computed Day's title reads to decide whether to name a day after its headline activity — "Denali Flightseeing" — instead of falling back to wherever that night's Stay is. When a day has several activities tied at the same top priority, the title joins their text with " & ", in sequence order. Deliberately generic rather than single-purpose: any future "what matters today" or trip-highlights view can read the same field without a new one being invented.
  • travelers is an excursion's own, directly authored roster — Trip.travelers[].id, the same link Package.travelers uses. It exists for exactly one case: an activity someone plans or books individually, where not every traveler is necessarily doing it — a shore excursion one family member skips, say. It's deliberately not read on a meal (mealType set) — a meal's real attendees are already derivable from diningFormat/includedIn against whichever Package backs it (trip-model.js's resolveMealTravelers), and authoring a second, competing traveler list on the same Activity would just invite the two to drift. Null is the default on every activity today, meaning either everyone's doing it or it just isn't decided yet — a day watching scenery go by from the ship, for instance, isn't an excursion at all and was never a candidate for this field, regardless of whether every traveler happens to be there.

The Ref shape, reusable beyond Note

type Ref =
  | { entity: 'trip'|'leg'|'stay'|'transit'|'route'|'activity'|'scenario'|'package'|'mealOption', id }
  | { date }
  | { dateRange: [start, end] }
  • kind replaces the old stored icon. The presentation tier maps kind ('warning' | 'footnote' | 'info') to icon and prominence itself.
  • Footnote numbers are never stored. They're assigned at render time, in the order notes are encountered on a given page — removing the exact hand-sync burden the current site's footnote system requires today.
  • concerns is reserved for annotation, not structure. Note today, a future Journal/actual-experience entry later, would reuse it — the strongly-typed foreign keys elsewhere (Stay.legId, Transit.routeId) stay exactly as they are, since those are structural, not annotative.
  • entity: 'mealOption' is the one Ref kind that's conditional, not just placed. Every other entity kind's notes always render wherever that entity itself shows up; a mealOption note only renders while its specific candidate is the one currently selected among its Activity's options — switching candidates in the UI swaps which of that Activity's notes are visible, same as switching a Scenario's ideal/alternate tab swaps which day's notes show. The Activity's own notes (entity: 'activity') are unaffected either way, since they're about the meal choice as a whole rather than any one candidate.

Open threads

→

Planned vs. actualStatus ladders are settled, but the mechanism for recording what really happened — a skipped activity, a rebooked flight — hasn't been designed. Ref/concerns is the likely vehicle: a future Journal entry pointing at whatever it's about, the same way Note does now.

→

Trip.travelersGained a stable id once Package.travelers needed something to link against, but is otherwise still just a lightweight embedded list. Undesigned: whether travelers need a fuller identity (for a multi-user "real app"), or an id is as far as this ever needs to go.

→

Booking as a formal typeTreated here as a shape repeated by convention across Leg, Stay, Transit, and Activity. In a real schema language this would likely become one named, shared type rather than four copies of the same core fields — increasingly true now that per-entity tests keep adding their own optional extensions to it (depositPaidAt/passengers on Leg, bookedThrough on Stay), the ferry test showed passengers itself is already reusable as-is on Transit, and the flight test forced bookedThrough from a flat string into its own { name, confirmationNumber } shape once a real booking needed two live confirmation codes at once.

→

Place beyond GoogleTested against a real Recreation.gov campsite reservation for a different trip (Channel Islands National Park — parsed to pressure-test this schema, deliberately not migrated in as that trip's data). Place.id currently assumes a Google Place ID, but a federal campground has its own resolvable id (recreation.gov/camping/campsites/4924) with no Google equivalent worth resolving against instead. Undesigned: whether Place gains a source discriminator so every embed site (Activity's place, Stay's lodging, Route's from/to/waypoints) can say which system an id belongs to, or a non-Google point stays out of Place entirely and lives as inline text the way Route's places already allows for a named-but-unresolved point.
